# SpecFrame for Product Teams

How product articulates capabilities and features for AI-assisted implementation.

## What This Is

When engineering uses an LLM to generate code, the LLM's output is only as good as the artifact it reads. PRDs are written for human stakeholders — they tell people what the product does and why. That's not enough for an LLM, which needs explicit boundaries, decision provenance, and rigor about edge cases that PRDs typically leave to interpretation.

The **specification** is the bridge: it takes the product intent captured in the PRD and restates it in a form the LLM can act on without improvisation.

This doc shows what product needs to produce so engineering's AI tooling can implement features cleanly — without back-and-forth, without the LLM guessing, and without rework.

## Where This Fits

```
Event Storming  →  PRD  →  Specification  →  Implementation Plan  →  Build  →  Verify  →  Ship
   (discovery)    (intent)   (LLM-readable)      (LLM-generated)
```

- **Event Storming** surfaces the business model — events, actors, processes, policies. Done once for a domain.
- **PRD** captures product intent for human stakeholders. What we're building, why, who it's for. Written in product language.
- **Specification** restates that intent in a form the LLM consumes. Same content; tighter form. Adds the rigor PRDs typically don't carry.
- **Implementation Plan** is generated by the LLM from the spec. Product doesn't write it.

The PRD doesn't go away. It feeds the spec.

## What the Spec Adds Beyond the PRD

PRDs are written assuming a human will interpret the gaps. The spec closes those gaps explicitly:

| PRD typically has       | Spec adds                                                                                                                              |
| ----------------------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| What the feature does   | **Out of Scope** — what's explicitly excluded (the LLM's main guardrail against drift)                                                 |
| Acceptance criteria     | **External Setup** — manual prerequisites the LLM can't do (account creation, OAuth config, API keys)                                  |
| Decisions made          | **Decisions tagged with provenance** — was this upfront, or surfaced during planning? Why?                                             |
| Data described in prose | **Data-model precision** — for each field, who sets it: client, DB default, RLS check, trigger? Conflating these creates silent bugs. |

## Spec Template

Required sections:

- **Objective** — one or two sentences: what and why
- **Scope** — what's included
- **Out of Scope** — what's explicitly excluded
- **Constraints** — non-negotiables (stack, compliance, perf, security)
- **Key Decisions Already Made** — anything the LLM should not second-guess
- **Acceptance Criteria** — how we know it's done

Optional sections (recommended for non-trivial features):

- **User Roles / Actors** — who interacts and what they can do
- **Business Rules** — specific logic the LLM needs to implement correctly
- **Data Model** — fields, types, and who sets each value (client / DB default / RLS check / trigger)
- **Dependencies** — other systems, services, features this depends on
- **External Setup** — manual prerequisites with timing

See `specification.md` for the full template doc with section descriptions and a complete TOTP worked example.

## How to Hand Off

1. Product writes the spec in `docs/work/<feature-name>/specification.md`.
2. Engineering prompts the LLM to generate an implementation plan from the spec.
3. The LLM surfaces gaps — decisions the spec didn't address (field length limits, pagination strategy, hosting choice, error handling, etc.). Expect this. It's the LLM earning its keep.
4. Product and engineering resolve the gaps; resolved decisions are added back to the spec, tagged `_(gap)_` so provenance is visible.
5. The LLM implements against the resolved spec.

If the spec is incomplete, the LLM either guesses (silent rework risk) or stops. Either way, the gap surfaces at planning time, not after the build.

## What Product Doesn't Worry About

- The implementation plan — the LLM generates it
- Technology choices — constraints belong in the spec; the LLM picks specifics within them
- Testing strategy — engineering owns it; product describes acceptance criteria
- Architecture — engineering owns it; the spec is _what_, not _how_

The spec is the _what_. The LLM and engineering own the _how_.

## Common Pitfalls

- **Treating the spec as an extended PRD.** It's not. It's a separate artifact. The PRD goes to stakeholders; the spec goes to the LLM. Use both.
- **Skipping Out of Scope.** This is the LLM's main guardrail. Without it, the LLM drifts into related-but-uncommitted work.
- **Vague data-model fields.** "Set by RLS" is wrong if the client must still provide the value — RLS validates, it doesn't populate. Be precise about who sets each field, or expect silent insert failures.
- **Burying decisions in chat.** Every decision goes in the spec. If it only lives in Slack/Teams/email, it's gone in three months.
